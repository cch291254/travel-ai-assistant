## 当前 RAG 流程

1. 读取最近最多六条历史消息，以及当前会话保存的待补充问题；若有待补充问题，先与本轮补充信息组合。
2. 调用一次改写模型，整理完整问题，判断是否需要澄清，并生成零至四个子问题及目标来源编号；单一需求可不拆分。
3. 需要澄清时，返回追问，不执行本轮检索、重排序和最终回答生成。
4. 信息足够时，对完整主问题与去重后的子问题分别召回最多七条候选、重排序保留最多三条。可靠匹配来源时按 `source_id` 过滤，否则不限定来源；全库检索不代表将全部切片交给模型。
5. 按 `chunk_id` 合并去重各分支证据，为合并结果统一编号。最多五路理论上保留十五条证据，不是整轮只保留三条；不再按段落强行只保留一片。
6. 将完整检索问题、证据上下文和本轮用户原文交给回答模型；不把旧助手的业务结论直接当成证据。
7. 解析回答 JSON，并检查声明的引用编号是否存在于本次证据映射中。

没有可用证据时，回答模块直接返回提示，不调用最终回答模型。引用编号存在性校验不等于引用内容一定支持结论，语义支持仍需效果评测。

改写、澄清判断和来源选择属于同一次模型调用，不是三个独立远程调用。正常有证据的流程通常包含一次改写调用和一次回答调用；重试可能增加实际请求次数。

### 当前配置

- 活跃集合名：`travel_documents_full_20161014_v2`；本地阶段测试为 201 片。v1 的 274 片保留作历史对照，不与 v2 混算。这是代码中的完整名称，请勿自行修正其中的日期数字。
- Chroma 目录：`data/chroma/`。
- Embedding：`BAAI/bge-m3`，归一化的 1024 维稠密向量。
- 向量化文本：标题路径加正文；库中分别保存原正文与元数据。
- Reranker：`BAAI/bge-reranker-v2-m3`。
- 切片：先合并同文档、同来源、同章节且有效期等不冲突的短段（短段阈值 50、目标 200、上限 400 字符），再按 400 字符、重叠 80 字符切分；不跨标题合并。
- 每路查询：`n_results=7`、`top_k=3`；完整主问题始终参与，子问题最多四个。
- 当前远程模型默认 `deepseek-flash`，思考关闭；改写输出上限 4048 tokens，回答默认上限 4028 tokens。环境变量可覆盖模型名。
- 两个本地模型输入上限均为 512 token，当前使用 CUDA 和半精度。
- 检索时两种本地模型交替占用 GPU；远程 DeepSeek 回答不在本机 GPU 上运行。
- 当前自动产品来源目录包含 S05、S06、S07，不等于完整知识库的全部来源目录。

API 资源在首次真实聊天调用时延迟加载，并在本进程内缓存。首次请求会包含模型初始化时间；即使本轮最终只需澄清，当前适配层也会先获取本地资源。`/health` 不加载模型。资源缓存不等于并发安全。

## API 与会话状态

- `GET /health`：服务健康状态。
- `POST /chat`：RAG 问答和会话保存。
- `GET /conversations/{conversation_id}`：读取本用户会话与消息。
- `DELETE /conversations/{conversation_id}`：删除本用户会话，并级联删除消息和追问状态。

除健康检查外，上述会话接口需要请求头 `Authorization: Bearer token_a` 或 `Bearer token_b`，分别对应演示用户 A 和 B。这些公开固定令牌仅用于本地演示，不是生产认证方案。

`/chat` 请求示例：

```json
{
  "question": "艾客旅游千岛湖套餐1几点、在哪里集合？",
  "conversation_id": null
}
```

后续请求携带首次返回的 `conversation_id`。客户端不提交可信历史和追问状态，后端按会话读取。问题去除首尾空白后长度为 1 至 1000 字符。

成功响应包含：

- `conversation_id`：当前会话 ID。
- `data.answer`：回答或澄清问句。
- `data.sources`：本轮回答声明引用的编号字符串列表。
- `citations`：引用编号、切片 ID 和元数据的映射，不包含正文。
- `evidence`：检索后合并保留的切片正文及元数据，不保证全部被引用。
- `rewrite_record`：改写调用统计；`record`：最终回答调用统计。
- `needs_clarification`：是否需要继续补充信息。

澄清轮没有检索证据和引用，最终回答调用记录为 `None`。待补充问题保存在数据库，不作为公开响应字段返回。再次澄清时保存组合后的问题；成功回答后清除追问状态，但保留聊天消息。

业务函数返回错误或没有可用结果时，API 返回 502，不保存本轮成功消息，也不覆盖数据库已有追问状态。未捕获的资源加载、检索或数据库异常不保证都映射为 502。401 表示令牌错误，403 表示会话不归当前用户，404 表示会话不存在；输入格式错误由请求校验处理。

## 本地数据分别存在哪里

- `data/conversation.db`：`conversations`、`messages`、`conversation_states`。保存会话、原始消息及待补充问题，不持久保存每轮证据、引用或 token 统计。
- `data/real_documents.db` 的 `documents`：早期导入解析登记，按内容哈希去重，保存成功或失败状态及错误原因；解析成功不等于向量索引成功。
- 同一数据库的 `document_indexes`：保存集合名、文档 ID、源文件绝对路径及上次完整索引操作成功时的文件哈希；以集合名和文档 ID 为联合主键。
- `data/chroma/`：向量、切片正文及来源元数据。
- `data/documents.db`：旧学习示例使用的登记库，不是当前管理入口使用的主登记库。

`document_indexes` 只记录经新带登记入口成功处理的文档，不会自动补齐首次批量建库的旧资料，也不保证在跨库操作部分失败后仍与向量内容完全一致。新管理入口不会自动重写早期 `documents` 导入记录。

## 单文档索引管理

先停止正在运行的 API 或独立 GPU 检索程序，备份需要保留的 `data/chroma/` 和 `data/real_documents.db`。当前 API 的线程锁不保护其他进程执行的管理命令。

帮助命令不修改资料：

```powershell
./.venv/Scripts/python.exe -B -m app.manage_documents --help
```

下面是会修改索引的操作示例。`your_existing_collection` 是占位符，必须替换为已核对的现有集合名；当前聊天使用的活跃集合名见“当前配置”。管理入口使用 `get_collection()`，不会自动创建一个不存在的集合。

### 新增或更新一份文档

```powershell
./.venv/Scripts/python.exe -B -m app.manage_documents index data/raw/tour_products.md --collection your_existing_collection
```

程序读取完整文件，解析、补充来源并重新切片，编码后写入或覆盖新切片，再删除该文档新版本不再包含的旧 ID。全部成功后，新增或更新 SQL 索引登记。

- `written`：本次提交写入的切片数，包含覆盖，不代表全部是新增。
- `deleted`：本次清理的过期切片数。
- 必须提交完整新文档，不能仅提交增量片段；空有效切片会拒绝更新。
- 哈希目前用于记录成功处理的版本，不会因哈希相同自动跳过重新编码。
- 当前 `document_id` 取文件名主体，例如 `tour_products.md` 对应 `tour_products`。同一集合中的不同文档不能使用相同文件名主体，包括不同目录或不同扩展名的同名文件。
- 文件改名会被识别为新的文档 ID，不会自动清理旧 ID；索引期间不要修改源文件。

### 删除一份文档的索引

```powershell
./.venv/Scripts/python.exe -B -m app.manage_documents delete tour_products --collection your_existing_collection
```

按提示准确输入大写 `DELETE` 才继续。程序先删除该文档的向量切片，再删除该集合中对应的 SQL 索引登记；切片已不存在时，仍会清理残留登记。

- `deleted_chunks`：本次选中删除的切片数量。
- `deleted_registration`：实际删除的登记行数，正常为 0 或 1。
- 不删除磁盘源文件，也不删除旧的 `documents` 导入记录。
- 删除不加载 Embedding 或 Reranker。
- 保留在 `data/raw/` 的文件，未来再次批量建库时仍会被读取。

向量操作和 SQLite 登记之间不是原子事务：先写新切片再清旧失败时可能新旧混存；向量操作成功而 SQL 失败时不会自动撤销向量修改。失败后应检查两边状态并重试或人工修复，不能只看登记表推断已回滚。操作完成后再启动 API。

## 当前限制与安全边界

- 不支持扫描 PDF、OCR、图片和复杂表格自动解析；不使用爬虫自动收集资料。
- 不提供实时天气、客流、交通、票价、库存或已核验的官方政策查询。
- 不提供订票、酒店代订、支付、合同或自动执行客户承诺。
- 不保证检索到全部必要证据。来源过滤、候选数量、模型输入截断和生成遗漏都可能影响结果。
- 引用编号合法不等于事实正确；旧资料、不同商品和不同版本不能混用。
- `/chat` 使用单进程线程锁串行处理。尚未实现异步并发调度、跨进程锁、完整超时取消和可靠幂等重试。
- 演示令牌和本地单用户资源管理不是生产安全方案；暂无文档管理页面及对应权限接口。
- 来源链接未经程序核验。不要将模型回复或未经核实的页面内容视为正式业务承诺。

## 附录：第六周 SQL 学习示例

这些是学习演示脚本，不是已接入 API 的会话存储模块。四个脚本只使用 Python 标准库，不调用模型 API。

- `examples/week6_day1_sql.py`：创建会话与消息表，启用外键，参数化写入和读取消息。
- `examples/week6_day1_read.py`：读取已有会话，验证合法关联与回滚、级联删除、其他会话不受影响，并练习 JOIN 与时间排序。测试中的写入、删除和时间修改最后回滚。
- `examples/week6_day1_user_test.py`：将创建会话和首条消息作为一组操作，演示成功提交与重新连接后的持久化读取。把消息内容改为 `None` 可验证约束失败后整组回滚。
- `examples/week6_day1_index.py`：比较联合索引创建前后的查询计划，并使用 JOIN 按用户筛选消息。

从项目根目录运行，例如：

```powershell
.\.venv\Scripts\python.exe examples\week6_day1_sql.py
```

`week6_day1_sql.py` 每次运行会新增两个会话和四条消息；`week6_day1_user_test.py` 的成功分支每次会新增一个测试会话和一条消息。只查询旧数据时不要重复执行这些 INSERT。

`week6_day1_read.py` 和索引示例保留课堂数据编号：会话 15、16，消息 18、19。新环境首次运行写入脚本会生成不同编号，需根据实际输出调整示例中的查询编号和排序测试消息编号；两条排序测试消息应属于要查询的会话。不存在或没有消息的会话不能作为级联删除验证的充分证据。

`week6_chat_demo.db` 与 `week6_chat_2_demo.db` 是本地生成的练习数据库，不进入 Git。不要将误拼的 `week_chat_demo.db` 当作原数据库。

索引一旦创建会保留，再次运行时两次查询计划都可能使用该索引。已观察到原查询计划从 `SCAN messages` 加临时排序，变为使用 `idx_messages_conversation_time` 的 `SEARCH`；尚未测量实际耗时提升。之前的 49 项核心自动测试不包含这些手工 SQL 实验。
