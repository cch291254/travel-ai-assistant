# 工具上下文优化记录（2026-10-29）

## 本次行为

- 同一轮工具聊天按 chunk_id 去重。每条工具消息只发送新增资料；已发送的资料保留在前面的消息里。
- 引用编号跨工具调用连续增长，合并保留旧编号与来源，供最终回答校验和页面展示使用。
- 内部检索由后端固定初召回 7 条、重排最多返回 3 条。模型只提供 query；多个查询合并后可以超过 3 条，没有全局 7 条上限。
- 发送给模型的 JSON Schema 去掉 title、default、pattern，保留字段用途和结构；服务端继续使用原 Pydantic 模型校验金额、人数及住宿参数。
- 本地日志记录模型输入/输出/合计 Token、模型与工具耗时、工具名称、检索条数和携带资料的字符数。当前排查日志也包含检索 query 和 chunk_id，不能视为完全脱敏。
- 每轮聊天最多 4 次模型请求、8 次工具执行。调用次数限制不等于累计 Token 预算；max_tokens=2048 仅限制单次模型输出。

## 本地日志与可选追踪

app.logging_config 为后端提供 request_id、控制台和 logs/app.log 输出。
app.tracing 由后端启动时初始化；LANGFUSE_ENABLED 默认为 false。启用时需在本地 .env 中配置 LANGFUSE_PUBLIC_KEY、LANGFUSE_SECRET_KEY、LANGFUSE_BASE_URL。
密钥、数据库和运行日志不随本次提交上传。模型自动评分不在本次提交范围内。

## 单题观察

新建会话，询问：客户逛完河坊街后想找一家适合聚餐的餐厅，希望既能吃鱼也能吃鸡，我可以向他推荐哪一家？

- 原始流程：9,094 Token。
- 每个工具结果仅发送新增资料：8,033 Token。
- 固定每次重排保留 3 条：7,645 Token。
- 加上工具说明精简：5,682 Token（两次模型请求分别为 1,852、3,830）。

最后一次相对最初下降约 37.5%。各次模型生成的检索词、重叠片段和回答长度存在变化，因此不能把全部差值归因于单项修改；这也不是全题集平均成本。
固定 3 条后，说明精简前后的比较中，首个模型请求输入从 2,482 降到 1,745 Token；此阶段尚未携带检索结果，支持说明精简减少输入开销的判断。
最后一次回答推荐五庄·江浙菜（河坊街店），给出鱼、鸡菜品依据并保留个人体验与接待信息待确认的边界；这里只完成该单题人工检查。
